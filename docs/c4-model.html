C4 Model · Context · Container · Component · Code

Credit Card Application

Two phases at four zoom levels: the applicant's intake, and four external checks run concurrently. The system gathers evidence and stops — nothing here decides. Each level answers one question and no more; a box only appears once its parent has been opened.

Scope intake + parallel checks Stack Spring Boot 4.1 · Java 21 · PostgreSQL Built FR1–FR5, FR7–FR9 Outside this project FR6 — three more providers (README Appendix A)
Built — code on main Designed, not yet built Outside the system boundary
Where this stops. The terminal state is CHECKS_COMPLETE: every evidence requirement answered or recorded UNAVAILABLE, every raw vendor response stored. Normalization, feature computation, the ruleset, manual review, provisioning and notification are a later increment and subscribe to the ChecksCompleted outbox event. No risk policy appears anywhere below, because none exists yet.

L2 element catalog
ContainerTechnologyResponsibilityState
Application API Spring Boot 4.1, Java 21, embedded Tomcat Every write to workflow state. Serves /v1/applications, runs the orchestrator and the five workers, calls the four providers. API built
Application Database PostgreSQL, Flyway, Hibernate Single source of truth. Also the job queue (vendor_check), the outbox, the inbox and the audit log — no broker in the topology. built
Document Store S3-compatible (LocalStack in dev) Holds uploaded bytes. Objects are written by the client and verified server-side before they can answer a requirement. FR3 built
  • No message broker. The outbox, the job queue and the webhook inbox are all Postgres tables, so a state change and its event commit together. Durability comes from the transaction, not from a second system that can disagree with the first.
  • No workflow engine. The durable workflow instance is the application's own process state — status, requirements, checks, outbox. Temporal or Camunda would be a second system of record that has to agree with the first.
  • Bytes bypass the API. The applicant PUTs directly to the object store with a short-lived pre-signed URL; the API only issues the URL and then verifies size, sha256 and magic bytes with a HEAD.
  • The workers are not a separate container. They are scheduled beans in the same process, claiming work with FOR UPDATE SKIP LOCKED — which is why scaling out to several instances needs no change to the queue design.

All nine states exist in code. SUBMITTED arrived with FR4, the checks states with FR5, APPROVED/REFERRED/DECLINED with FR8 and EXPIRED with FR9; none needed a migration, because status is stored as text. Every transition records statusChangedAt, which the deadlines read. id is pre-assigned and time-ordered, so ORDER BY id DESC replaces a created_at column; version is Long, not long, because Spring Data reads null as "new" and calls persist instead of merge. Every declared field is a value object that validates in its constructor, so every instance is valid and the DTO fields are unannotated on purpose — the rule cannot be bypassed. FirstName and LastName are distinct types sharing NameRules, so the compiler refuses to swap them, and the limit is 70 code points each rather than 100 shared. DateOfBirth's floor is the absolute date 1900-01-01, not "within 120 years": a relative bound would make an applicant's own row fail to load once they aged past it, because the converter routes every load through the constructor.

The hierarchy is flat on purpose. Every exception extends DomainException directly and names its category (422 / 409 / 404), so adding a refusal is one class and nothing else, and ApiExceptionHandler switches exhaustively — a new category breaks the build while a new exception of an existing category needs no web change. code() derives the problem type from the class name (DraftAlreadyExistsException → draft-already-exists) except where the category fixes it: every not-found looks alike so ids can't be probed, and an invalid value is a malformed request like any other.

  PROC->>DB: one tx — SUBMITTED to VERIFYING, IDENTITY requirement PENDING, IDV vendor_check QUEUED
  VW->>DB: claim — FOR UPDATE SKIP LOCKED, lease 1 min
  VW->>IDV: create applicant (id stored), upload document, create check
  IDV-->>VW: check id, in progress
  VW->>DB: tx — AWAITING_CALLBACK, 30 min deadline
  IDV->>API: webhook — a notification only, never the result
  API->>DB: INSERT vendor_inbox ON CONFLICT DO NOTHING, then 200 fast
  IW->>IDV: GET check and report — the result is always fetched
  IW->>DB: UPDATE … WHERE status = 'AWAITING_CALLBACK', plus outbox VendorCheckCompleted
  DB-->>RL: VendorCheckCompleted
  RL->>PROC: VendorCheckCompleted
  PROC->>DB: tx — requirement RECEIVED, evaluate returns Complete, VERIFYING to CHECKS_COMPLETE, outbox ChecksCompleted
  DB-->>RL: ChecksCompleted
  RL->>PROC: ChecksCompleted
  PROC->>DB: tx — decide (FR8): clean result to APPROVED, anything else to REFERRED; audit DecisionMade
  P->>API: GET /v1/applications/{id}
  API-->>P: 200 APPROVED or REFERRED — never the reason
  Note over PROC: No webhook? The Reconciler polls the same check.<br/>No answer by the deadline? FAILED, UNAVAILABLE, REFERRED.
